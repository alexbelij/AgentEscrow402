# T3.2 — Gaming-reward escrow with Merkle proof of results

**Status:** ✅ Implemented (server side + API)
**Files:** `server/gaming_reward.py`, `server/gaming_reward_api.py`, `tests/test_gaming_reward{,_api}.py`
**Endpoints:** `/gaming/commit`, `/gaming/lock`, `/gaming/proof/{root}/{player_id}`, `/gaming/claim`, `/gaming/escrow/{escrow_id}`

## Problem

On-chain gaming and tournament platforms want a trust-minimised way to
distribute prize pools:

* The operator computes the leaderboard off-chain (the tournament ran
  server-side, or on another chain).
* Publishing the full leaderboard is expensive and often privacy-hostile
  (losers don't want their score public).
* But winners need to be able to **prove independently** that they earned
  their reward without the operator's cooperation for each payout.

## Design

Each round produces a **reward sheet** — a mapping
`{player_id → (reward_amount, rank)}`. The operator commits to it by
publishing only a Merkle root; each winner receives an inclusion proof
they can submit to the escrow contract to claim their reward.

### Leaf shape

```
leaf_hash = sha256("<player_id>:<reward_amount>:<rank>")
```

* `player_id` — natural key (agent id, wallet, hashed handle)
* `reward_amount` — in the escrow's unit (motes for Casper)
* `rank` — leaderboard position; part of the leaf so a claim commits to
  a specific placement (not just an amount)

### Tree math

Standard binary Merkle:

* Parent = `sha256(left || right)`
* Odd level: duplicate the last node
* Empty sheet has stable root `sha256("empty-rewards")` so a zero-winner
  round is still a valid commitment (the escrow just refunds the pool)

The tree layout is identical to `merkle_provenance.py`; only the leaf
pre-image differs (reward-shaped vs evidence-shaped). This means proofs
are cross-verifiable in TS with the same `merkleProvenance.ts` helper if
callers reshape the leaf pre-image.

## Flow

1. **Commit** — operator uploads the sheet to `/gaming/commit`. Server
   returns `RewardCommitment(root, total_committed, winners_count)`.
   Sheet is cached in-memory for proof lookups (moves to Postgres in a
   follow-up commit; the math is unchanged).

2. **Lock** — operator opens an escrow via `/gaming/lock` against a
   committed round. The server refuses to lock if
   `total_committed > prize_pool_motes` (solvency guard).

3. **Prove** — a winner (or the operator on their behalf) calls
   `GET /gaming/proof/{root}/{player_id}` to fetch their inclusion
   proof. Anyone with the root can verify a proof client-side —
   see `verify_claim` in `server/gaming_reward.py`.

4. **Claim** — winner submits `POST /gaming/claim` with their proof.
   `evaluate_claim` runs three checks atomically inside a per-escrow
   asyncio lock:
   * proof verifies against `locked_root` (rejects amount inflation,
     rank swap, foreign player, sibling injection, malformed proof)
   * player hasn't claimed before (rejects double-claim)
   * `reward_amount ≤ remaining_pool` (rejects over-pool)

   On success, decrements the pool and marks the player claimed.

5. **Inspect** — `GET /gaming/escrow/{escrow_id}` returns the live
   claim state (remaining pool, claimed players).

## Security properties

| Attack | Defence |
|--------|---------|
| Winner inflates their reward amount | Leaf hash changes → proof fails |
| Non-winner submits fabricated proof | No path exists to the locked root; verification fails |
| Winner claims twice | `already_claimed` set — rejected before pool decrement |
| Operator commits a sheet whose sum exceeds the pool | `/gaming/lock` refuses (`insolvent commitment`) |
| Two winners claim simultaneously | Per-escrow asyncio lock serialises the decrement |
| Duplicate `player_id` on sheet | Rejected at `/gaming/commit` (`duplicate player_id`) |
| Cross-sheet proof reuse (proof from round A vs root of round B) | Root differs, verification fails |

## Storage (deferred)

`_SHEETS` and `_ESCROWS` are in-memory dicts protected by an
asyncio.Lock per escrow. Persistence is a mechanical follow-up:

* Add two tables (`gaming_sheets`, `gaming_escrows`) with a JSONB
  column for the leaves and a `claimed_players` array.
* Wrap the claim decrement in a serialisable transaction (or `UPDATE …
  WHERE remaining_pool ≥ amount RETURNING`).
* Keep the API contract as-is.

The demo doesn't need it — the crypto and the API contract are the
deliverable.

## What this unlocks

* Any on-chain game / tournament / raffle can distribute rewards with
  one root pinned on-chain, unlimited winners, and O(log N) proof size
  per claim.
* Losers' scores stay private (their leaves are never revealed).
* Combined with T3.1 threshold-secret escrow, a tournament operator
  can require an n-of-m arbitration committee before roots become
  claimable (fraud-proof gating).
