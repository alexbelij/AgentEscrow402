# T3.3 — On-chain batch cap/quorum guard

**Status:** Server-side reference implementation complete (this doc).
WASM transliteration is the follow-up item on the Tier 3 roadmap.

## Problem

Before T3.3, the escrow-manager Rust contract enforced the release-cap /
arbiter-quorum rule only on *single* `release()` calls. `batch_release()`
took a list of service hashes and released them in one deploy without an
on-chain cap check.

The backend patched over that gap with an ad-hoc validation block inlined
in `server/app.py::batch_release_escrows`: iterate the batch, load each
escrow from the sandbox store, if any exceed the release cap require an
arbiter quorum. Functional, but:

* Two code paths could drift — the sandbox path (Python) and the live
  path (Rust WASM, missing).
* No dry-run: an SDK client had to actually POST the mutating route to
  discover a batch would be rejected, which is expensive on gas.
* Failure modes were unstructured `HTTPException(422, detail=<str>)`,
  so clients had to string-match to know *why* a batch was rejected.

## What T3.3 ships

1. **A pure, deterministic validator** — `server/batch_guard.py`.
   No I/O, no time-of-day, no side effects. Given
   `(action, service_hashes, snapshots, release_cap_motes,
   arbiter_registered, arbiter_threshold, arbiter_pubkeys,
   arbiter_signatures)` it returns a `BatchDecision` with:

   * `admit: bool` — the whole batch verdict (all-or-nothing).
   * `needs_quorum: bool` — whether *any* escrow was above cap.
   * `valid_arbiter_votes: int` — the tightest per-escrow bottleneck.
   * `required_quorum: int` — echoed from config.
   * `above_cap_hashes: tuple[str, ...]` — the offenders.
   * `rejections: tuple[BatchRejection, ...]` — ordered typed reasons.

2. **A dry-run preview endpoint** — `POST /escrows/batch-preview`.
   Returns the same `BatchDecision` the mutating routes would compute,
   without hitting Casper or updating any local state. A 200 is *not*
   an admit — inspect `admit` in the body.

3. **Refactored `/escrows/batch-release` and `/escrows/batch-cancel`**
   to call the same guard, so the two paths cannot drift. This is the
   Python oracle the Rust follow-up will be diffed against.

4. **Stable rejection codes**:

   | Code | Meaning |
   |------|---------|
   | `empty_batch` | `service_hashes` list is empty |
   | `batch_too_large` | Exceeds `MAX_BATCH_SIZE` (50) |
   | `unknown_action` | Not `release` or `cancel` |
   | `arbiter_list_length_mismatch` | `pubkeys` and `signatures` have different lengths |
   | `duplicate_service_hash` | Same escrow listed more than once in one batch |
   | `escrow_not_found` | Snapshot missing for a listed hash |
   | `escrow_not_pending` | Escrow is `released` / `cancelled` / `disputed` |
   | `quorum_shortfall` | Above-cap escrow lacks the required arbiter votes |

   Codes are safe to switch on in a client; messages are for humans.

## Invariants worth naming

* **All-or-nothing.** A single per-escrow failure rejects the whole batch.
* **Vote-to-escrow binding.** A cap-approval signature over
  `release:<service_hash>:cap_approval` is bound to *one* escrow — the
  guard does not credit a vote for escrow A toward escrow B, even inside
  the same batch. Prevents a relayer from paying one arbiter to unlock
  many escrows.
* **Duplicate pubkeys count once.** The guard deduplicates by pubkey
  *per escrow*, so a signer submitting twice cannot double-count.
* **Cancel never needs quorum.** The refund path is unconditional
  (subject to on-chain caller-authorization); the guard enforces this
  invariant even if a client mistakenly supplies arbiter votes.
* **Empty registered arbiter set ⇒ above-cap admissible.** Same
  escape-hatch parity as the previous inlined logic: with no arbiters
  registered, the pod passes the batch through to Casper, and the
  contract's own guard is the last line of defence. (The new WASM check
  will remove this escape hatch — a batch above cap will simply fail on
  chain if no arbiter set exists.)

## Canonical cap-approval message

Identical to the existing single-`release()` A1 hardening:

```
{action}:{service_hash}:cap_approval
```

where `action ∈ {"release", "reveal_swap"}` and `service_hash` is the
lowercase-hex 32-byte escrow id. See
`server/arbiter_crypto.py::build_cap_approval_message` and
`contracts/escrow/src/main.rs::build_cap_approval_message`.

Ed25519 only for arbiter signing keys (secp256k1 arbiters not modelled).

## API

### `POST /escrows/batch-preview`

Request:

```json
{
  "action": "release",
  "service_hashes": ["<64-hex>", "<64-hex>"],
  "arbiter_pubkeys":    ["01<pk-hex>", "01<pk-hex>"],
  "arbiter_signatures": ["01<sig-hex>", "01<sig-hex>"]
}
```

Response (always 200 for a well-formed body):

```json
{
  "admit": false,
  "action": "release",
  "needs_quorum": true,
  "valid_arbiter_votes": 1,
  "required_quorum": 2,
  "above_cap_hashes": ["<64-hex>"],
  "rejections": [
    {
      "code": "quorum_shortfall",
      "message": "escrow abcdef01234567… exceeds release_cap (1000 motes); only 1 valid arbiter signature(s), need >= 2",
      "service_hash": "<64-hex>",
      "detail": { "valid_votes": 1, "required": 2, "amount_motes": 10000, "release_cap_motes": 1000 }
    }
  ],
  "max_batch_size": 50
}
```

## WASM migration (follow-up)

The Python `evaluate_batch` is intentionally a straight port target for
Rust. The upcoming `contracts/escrow/src/main.rs::batch_release` will:

1. Iterate `service_hashes` from the URef list arg.
2. For each `service_hash`, `read` the escrow record from the contract's
   named-key dictionary.
3. Reuse `build_cap_approval_message` (already there).
4. Count valid votes per hash and enforce the threshold *per hash*.
5. Reject the whole deploy on any per-escrow failure.

Once merged, the Python guard becomes a fast-fail pre-flight only; the
on-chain check is the authoritative one. Regression fixtures for parity
diff-testing:

* `tests/test_batch_guard.py` (19 tests, unit-level oracle)
* `tests/test_batch_guard_api.py` (10 tests, end-to-end)

Both suites are green on `tier-wow-and-3/main-block` as of T3.3 commit.

## Non-goals for T3.3

* Rewriting the escrow-manager WASM. Tracked separately.
* Producing arbiter signatures — those are minted on the client side,
  outside the pod's trust boundary.
* Signalling *partial* success (release the below-cap subset, defer the
  above-cap ones). Explicit design choice: batches are atomic.
