# T3.1 — Threshold Escrow MPC (Shamir Secret Sharing)

**Status:** shipped — Tier 3, item 1/7.

## Problem

A single "release-key holder" is a single point of failure for AE402 escrow release:
- one compromised arbiter can leak the release key → agent funds drained
- one offline arbiter can block release → funds locked
- concentrating trust in a single hardware-security-module operator undermines the
  decentralised-arbitration model

## Design

Split the release-authorization secret across `m` independent holders such that
**any `n` of them** (n ≤ m) can jointly authorise release, but any coalition of
fewer than `n` learns nothing about the secret (information-theoretic).

We use **Shamir Secret Sharing** over the finite field of secp256k1 curve order
(≈ 2²⁵⁶). Random polynomial of degree `n-1` with the secret as constant term;
each share is `(x_i, poly(x_i))` for x_i ∈ {1..m}.

Reconstruction: Lagrange interpolation at x=0.

### Above the SSS primitive

`build_threshold_release(payload, threshold, total)`:
1. Generate random 32-byte key `K`.
2. AEAD-encrypt the release payload with `K` (HKDF-SHA256 → HMAC-SHA256 CTR + MAC).
3. Split `K` into `total` Shamir shares with reconstruction threshold `threshold`.
4. Return `(encrypted_payload, [share_1, ..., share_total], threshold, total)`.

Release path: collect ≥ threshold shares → reconstruct K → decrypt payload → act.

## Wire formats

Share (hex-encoded, 68 chars): `IIII || VVVV..VVVV` where `IIII` is the 2-byte
index (1..255) and `VVVV..VVVV` is the 32-byte y-value.

Encrypted payload: `IV(16) || ciphertext || MAC(32)`.

## Security properties

| Property | Guarantee |
|---|---|
| n-1 shares reveal nothing | information-theoretic (Shamir) |
| Share tamper | Reconstruction gives wrong K → AEAD MAC fails |
| Wrong bundle's shares | AEAD MAC fails (each bundle has fresh random K) |
| Share order | Lagrange interp is order-independent |
| Share reuse across bundles | Not possible — K is fresh per `build_threshold_release` |

## Non-goals (v1)

- **Verifiable Secret Sharing** (Feldman/Pedersen VSS): dealer cannot be verified
  as honest by shareholders — trusted-dealer model. Deferred to T3.1b.
- **Proactive resharing:** shares are static. Rotation requires re-splitting.
- **Multi-party computation of the release action itself:** we do reconstruct-then-act,
  not compute-in-shares. Reconstruction happens at the aggregator (server), which
  must be trusted at the moment of release. For full non-interactive threshold
  signatures, see FROST-style DKG — a future extension.
- **On-chain enforcement:** on-chain contract does not validate the share
  reconstruction; it trusts the release-authorization signature. Threshold gate
  is off-chain.

## API

### `POST /threshold/split`
```json
{"payload_b64": "...", "threshold": 3, "total_shares": 5}
```
→ `{"encrypted_payload_b64": "...", "shares_hex": [...], "threshold": 3, "total": 5}`

### `POST /threshold/reconstruct`
```json
{"encrypted_payload_b64": "...", "shares_hex": [...], "threshold": 3}
```
→ `{"payload_b64": "...", "shares_used": 3}`

### `GET /threshold/config`
Describes supported parameter ranges and algorithm choices.

## Operational recommendation

- Distribute shares over independent channels to independent holders. AE402
  server should **not** retain shares after split.
- Store `encrypted_payload` in the escrow row / off-chain store. It is not
  sensitive on its own.
- Typical parameterisations for AE402:
  - **3-of-5:** high availability + break-glass (2 offline is OK)
  - **2-of-3:** minimal decentralisation, escrow demo/dev
  - **5-of-7:** high-value production escrow with wide arbiter council
