# T3.7 — Compliance framework for regulated jurisdictions

**Status:** Reference policy engine complete (this doc). Not legal advice,
not a regulator-certified compliance product — see "Scope and honesty"
below before anyone reads this as more than it is.

## Problem

AgentEscrow402 lets any two agents create and settle an escrow with no
jurisdiction-awareness at all. That's fine for a hackathon demo; it's not
fine for anything real. Every serious agent-to-agent payment rail that
wants regulated counterparties eventually needs three things:

1. A way to say "this counterparty is in a jurisdiction we can't serve at
   all" (sanctions/embargo-style blocking).
2. A way to say "this counterparty is in a jurisdiction we can serve, but
   only above a KYC bar, and only up to a cap" (restricted-jurisdiction
   licensing gaps — most of the world, most of the time).
3. A way to flag transactions that need a compliance record even when
   they're otherwise permitted (travel-rule / large-transaction
   reporting).

Before T3.7 none of this existed anywhere in the codebase.

## What T3.7 ships

1. **A pure, deterministic policy engine** — `server/compliance.py`.
   No I/O, no wall-clock reads, no chain calls. `ComplianceEngine.evaluate()`
   takes `(country_code, verification_level, amount_motes,
   prior_volume_today_motes)` and returns a `ComplianceDecision`:

   * `permitted: bool` — the enforceable verdict.
   * `requires_reporting: bool` + `report_reasons: tuple[ReportReason, ...]`
     — **independent of `permitted`**. A transaction can be permitted and
     still require a compliance record (restricted-jurisdiction activity,
     a large transaction, approaching a daily cap) — that mirrors how
     real travel-rule / large-transaction-reporting regimes actually work,
     where reporting and permission are separate axes.
   * `rejections: tuple[ComplianceRejection, ...]` — every reason it
     failed, not just the first (a transaction can be both under-KYC'd
     *and* over the cap at once; both show up).
   * `regime`, `verification_level`, `amount_motes`, `policy_notes` echoed
     back so a client never has to re-derive "why" from scratch — same
     shape convention as T3.3's `BatchDecision`.

2. **KYC tiering reuses the identity registry's `VerificationLevel`**
   (`UNVERIFIED` / `BASIC` / `ENHANCED` / `FULL` from
   `server/identity_registry.py`) instead of inventing a second notion of
   "how verified is this agent". `/compliance/evaluate-by-agent` reads the
   tier **live** from the registry by DID — a client cannot claim a higher
   KYC tier than the registry actually has on file; the request schema for
   that route has no `verification_level` field at all, so there's nothing
   to spoof.

3. **A small illustrative jurisdiction table**, not a real sanctions list:

   | Country | Regime | Min KYC | Single-tx cap | Daily cap |
   |---|---|---|---|---|
   | US, GB, SG | `UNRESTRICTED` | — | — | — |
   | NG | `RESTRICTED` | ENHANCED | 5,000 CSPR | 20,000 CSPR |
   | TR | `RESTRICTED` | BASIC | 10,000 CSPR | 50,000 CSPR |
   | VE | `RESTRICTED` | FULL | 1,000 CSPR | 5,000 CSPR |
   | KP, IR | `PROHIBITED` | — | — | — |

   `ComplianceEngine(policies=...)` takes the whole table as a constructor
   argument — the default above is a *fixture*, swapped wholesale before
   any real deployment. An unrecognized country code **fails closed**
   (`unknown_jurisdiction` rejection, treated as the most conservative
   `PROHIBITED` regime) rather than silently passing as unrestricted —
   same "unknown is a rejection, not a pass" posture as T3.3's
   `unknown_action` code.

4. **A global large-transaction reporting threshold** (10,000 CSPR
   default, echoing the real-world $10k/€10k large-transaction-reporting
   convention as a round-number illustrative default) — any transaction at
   or above it is flagged `LARGE_TRANSACTION` regardless of jurisdiction.

5. **`/compliance/*` API** (`server/compliance_api.py`):
   * `GET /compliance/jurisdictions` — read-only listing of the configured
     table, sorted by country code.
   * `POST /compliance/evaluate` — dry-run evaluation for an explicit
     `(country, KYC tier, amount)` triple. Never mutates state; a policy
     rejection is `permitted: false` in a 200 body, not an HTTP error —
     same non-mutating-preview convention as T3.3's `/batch-preview`.
   * `POST /compliance/evaluate-by-agent` — same evaluation, but resolves
     `verification_level` from the live identity registry by DID (404 if
     the DID isn't registered).

## Scope and honesty

This is a **reference policy engine**, not a compliance product:

* The jurisdiction table is illustrative. It is not sourced from OFAC, the
  FATF grey/black lists, or any real VASP licensing tracker. Replace it
  before this touches a real transaction.
* No real sanctions data feed, no real travel-rule counterparty data
  exchange (IVMS 101 / TRUST / Notabene-style protocols), no tax
  reporting, no securities analysis, no licensing determination.
* `prior_volume_today_motes` is caller-supplied — this module has no
  persistence layer for rolling transaction history, on purpose (same
  separation as `batch_guard.py` taking pre-fetched escrow snapshots
  instead of hitting the store itself). A real deployment wires a
  per-counterparty rolling-window aggregator and passes the result in.
* `evaluate-by-agent`'s DID→verification-level binding closes the
  "client-supplied KYC tier" spoofing gap, but the KYC *tier itself* is
  only as trustworthy as whatever process advances an identity's
  verification level in the registry — T3.7 does not ship that process
  (identity document review, liveness check, etc. are out of scope here,
  same as they're out of scope for `identity_registry.py`).

## Tests

40 unit tests (`tests/test_compliance.py`, including 3 hypothesis
property tests: prohibited-jurisdictions are never permitted regardless of
amount, unrestricted-jurisdiction transactions below the reporting
threshold never require reporting, and unknown jurisdictions always fail
closed regardless of verification tier or amount) + 15 API tests
(`tests/test_compliance_api.py`, including the DID-spoofing-is-impossible
check and a same-input/same-output determinism check). Full suite after
T3.7: 1321 passed, 1 skipped, zero regressions.
