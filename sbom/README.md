# Software Bill of Materials (SBOM)

CycloneDX SBOMs for every dependency graph in this repo, generated for the T14 hackathon deliverable.

| File | Ecosystem | Source |
|---|---|---|
| `python-sbom.json` | Python | `requirements.txt` (server + tests), via `cyclonedx-py requirements` |
| `frontend-sbom.json` | Node.js | `frontend/` (Vite/React judge & lab UI), via `@cyclonedx/cyclonedx-npm` |
| `server-casper-tx-sbom.json` | Node.js | `server/casper_tx/` (on-chain tx scripts), via `@cyclonedx/cyclonedx-npm` |
| `rust-contracts/*.cdx.json` | Rust | one CycloneDX doc per contract crate in `contracts/`, via `cargo cyclonedx --all` |

## Regenerating

```bash
# Python
pip install cyclonedx-bom
python -m cyclonedx_py requirements -i requirements.txt -o sbom/python-sbom.json --of json

# Node (frontend)
cd frontend && npx @cyclonedx/cyclonedx-npm --ignore-npm-errors --output-file ../sbom/frontend-sbom.json

# Node (casper_tx scripts) — MUST run `npm install` first or the SBOM
# will silently emit `components: []` (cyclonedx-npm introspects
# node_modules, not just package.json).
cd server/casper_tx && npm install --no-audit --no-fund && \
  npx @cyclonedx/cyclonedx-npm --ignore-npm-errors --output-file ../../sbom/server-casper-tx-sbom.json

# Rust (all contract crates)
cargo install cargo-cyclonedx
cd contracts && cargo cyclonedx --format json --all
# then move the generated *.cdx.json files from each crate dir into sbom/rust-contracts/
```

All formats use the CycloneDX 1.x JSON schema and can be scanned by any CycloneDX-compatible SCA tool
(Dependency-Track, Grype, OWASP Dependency-Check, Snyk, etc.).

## Known caveats

- **Python SBOM depth**: `cyclonedx-py requirements` reads the manifest, not an
  installed environment or lockfile, so `python-sbom.json` covers direct
  dependencies from `requirements.txt` (7 packages) but does not enumerate
  their transitive graph. Consumers who need the full transitive tree should
  regenerate from a resolved lockfile (e.g. `pip-compile -o requirements.lock`
  then `cyclonedx-py requirements requirements.lock`).
- **Node SBOMs require `node_modules`**: both `frontend/` and
  `server/casper_tx/` SBOMs are generated by `cyclonedx-npm`, which reads the
  installed dependency tree. Regeneration steps above install first for this
  reason. Skipping the install step will silently emit an empty `components`
  array with no error — the CI regeneration guard exists to catch that.

## CI regeneration guard

`.github/workflows/sbom-guard.yml` regenerates every SBOM from scratch on
push/PR to `main` and fails the build if any regenerated SBOM's
component set (name + version + purl) drifts from the checked-in copy.
This prevents:

- Dependency upgrades landing without an SBOM refresh.
- Silently-empty SBOMs (e.g. missing-`node_modules` bug that hit
  `server-casper-tx-sbom.json` in the original T14 delivery).
- New workspace crates or npm dependencies not being picked up.

When the guard fails, regenerate locally with the commands above and
commit the refreshed SBOMs into the same PR.
